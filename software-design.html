Software design

Doc4CF brings two earlier projects into one corpus reference. Doc4TF supplies the idea of a dedicated documentation page for each feature. TF_Knowledge_Graph provides the model for connecting features to the node types they annotate.

In Doc4CF, Context-Fabric reads the corpus once per build. The same feature profile supplies both the coverage table on a feature page and its connections in the graph. A reader can follow a connection to a node type, see which other features occur there, and open their documentation. For a query author, this identifies which node line can carry a constraint. The next decision is how that node relates to the other nodes in the question. See worked Context-Fabric search templates.

Doc4CF does the corpus analysis at build time. Python and Context-Fabric read one corpus version and produce a directory of HTML, CSS, JavaScript and JSON. Once the files are written, a reader can browse the reference offline.

Reading a corpus

The generator discovers the .tf files in the input directory and reads their UTF-8 headers. Context-Fabric uses otype to identify node types and oslots to associate nodes with their smallest textual units, called slots. The corpus determines whether a slot is a word, a sign or another unit.

When the corpus supplies text templates, Doc4CF asks Context-Fabric to render the first twelve nodes of each template’s target type. A sign-level corpus can therefore show both sign and word renderings. Without templates, the reference lists string-valued fields observed on slots and shows samples.

From measurements to pages

For a node feature, the generator counts populated nodes by type and tallies their values. For an edge feature, it also counts destinations by type. These profiles supply the feature pages and the feature-to-type links in the knowledge graph.

The diagram orders types by their average slot coverage and places each feature near the types it annotates. A high position indicates broad coverage. To determine containment between particular nodes, one would need to compare their individual slot memberships.

Optional language-model descriptions

With --model, the build sends a feature profile to the selected LLM provider and adds the returned paragraph to the feature page. Each request is independent. Optional editor notes supply shared corpus background to every selected feature, and only those features receive generated prose. Doc4CF caches the response text and reported model ID under a hash of the request. The contents of the notes contribute to that hash; their filename does not. The build reads the selected provider’s API key from the environment. The install guide describes provider selection and model credits.

Readers can compare the labeled prose with the original metadata and observed counts on the same page.

What runs in the browser

Local JavaScript filters the feature index and responds to selections in the graph explorer and corpus diagram. The graph data needed by these views is embedded in their pages. The JSON export follows the original project’s node dictionary, typed IDs and directed “valid on” edges. Doc4CF adds a config_feature node category and omits the original per-edge freqDetail frequency breakdown.
