Install guide

Runtime options · Provider keys · Run from Python · Review dataset notes

Install Doc4CF with pip

Use Python 3.13 or newer in an activated virtual environment. To install Doc4CF from a package index that hosts it, run:

python -m pip install doc4cf

For the current private distribution, install the supplied wheel:

python -m pip install ./doc4cf-0.1.0-py3-none-any.whl

Build your first corpus site

Point Doc4CF at the directory containing otype.tf and oslots.tf. Give it a fresh output directory as the second argument.

doc4cf path/to/corpus/tf/VERSION site

Open site/index.html in your browser. Use doc4cf --help to see the available options.

Runtime options

Use doc4cf CORPUS OUTPUT [options] in a terminal. The same arguments work with python -m doc4cf. Only the two paths are required.

corpus
Directory containing the TF files for one dataset version, for example N1904/tf/1.0.0.
output
Destination directory for the generated HTML and assets. Choose a fresh directory to keep previous builds.
--project-home URL
Add a footer link to a parent project. Omit for a standalone corpus site. A relative URL such as ../../index.html is relative to the corpus overview.
--provider NAME
Select openrouter (default), openai, groq, gemini, or anthropic. Used when a model is supplied.
--model ID
Enable generated descriptions with a chat model available through that provider. Omit for an offline build.
--dataset-context FILE
Include optional UTF-8 text or Markdown notes in each request. Requires --model.
--describe-features NAMES
Enrich only the listed features, for example lemma,tense,frame. Requires --model. The default selects all features for enrichment when a model is enabled.
--model-attribution MODE
Show provider and model on each enriched feature page (default), once on the overview, or use none to hide the names.
--cache DIR
Store generated descriptions for reuse. The default is .doc4cf-cache under the working directory. Use the same cache for trial and final builds.
-h, --help
Print the options for the installed version and exit.

Levels of inference

Doc4CF reads declared section names and text templates from the corpus metadata. It measures feature coverage and value frequencies directly. The diagram then uses average slot coverage to order node types from broadest to finest. That layout helps readers explore overlapping units without assuming they form a strict hierarchy.

Provider accounts and API keys

An API key is a secret issued by the service that runs your model. For example, OPENROUTER_API_KEY is the name Doc4CF looks up in the build process’s environment. Its value is the key you copy from your OpenRouter account. The model ID is a separate value supplied with --model.

  • OpenRouter — select openrouter and use OPENROUTER_API_KEY. The example model openrouter/free selects the free router. Create an OpenRouter key.
  • OpenAI — select openai and use OPENAI_API_KEY. Choose a Chat Completions model available to your OpenAI API project. Create an OpenAI project key.
  • Groq — select groq and use GROQ_API_KEY. Copy a chat model ID from the Groq model catalog. Create a Groq key.
  • Google Gemini — select gemini and use GEMINI_API_KEY. Choose a Gemini chat model available through the Gemini API. Create a Gemini key in Google AI Studio.
  • Anthropic Claude — select anthropic, set ANTHROPIC_API_KEY, and use a Claude model ID available to your Anthropic API account. For a key that requires an explicit workspace, also set ANTHROPIC_WORKSPACE_ID. Create a Claude API key.

Set the key for the service you call. For example, when accessing a model through OpenRouter, use the OpenRouter key even if another company made the model. Calling that company’s API directly uses its own key and account quota.

Run Doc4CF from Python or a notebook

Run this in the Python environment where you installed Doc4CF. Set provider to one of the five names above and enter the TF directory and model ID. Python reuses an existing environment variable when available. Otherwise it asks for the key using a hidden prompt and passes it to the build process.

from getpass import getpass
import os
import subprocess
import sys

provider = "openrouter"  # or "anthropic", "openai", "groq", "gemini"
model = "openrouter/free"  # replace with a model ID for your provider
key_name = {
    "openrouter": "OPENROUTER_API_KEY",
    "openai": "OPENAI_API_KEY",
    "groq": "GROQ_API_KEY",
    "gemini": "GEMINI_API_KEY",
    "anthropic": "ANTHROPIC_API_KEY",
}[provider]

env = os.environ.copy()
if not env.get(key_name):
    env[key_name] = getpass(f"Enter your {provider} API key: ").strip()

subprocess.run([
    sys.executable, "-m", "doc4cf", "N1904/tf/1.0.0", "review-site",
    "--provider", provider, "--model", model,
    "--describe-features", "lemma", "--model-attribution", "overview",
], env=env, check=True)

This builds the complete N1904 reference and requests prose only for lemma. For a different provider, change both provider and model; the dictionary chooses the matching key. A key entered at the prompt is available to this run. Keep its value out of notebooks, command arguments, context files, and version control. Offline builds need no provider account or key.

Try your dataset notes on three features

Save a short UTF-8 text or Markdown file, for example n1904-notes.md. Include conventions or verified definitions the model cannot learn from counts alone. A useful note for N1904 is “A lemma may also be recorded on a phrase or subphrase. Count word nodes when reporting word occurrences.”

doc4cf N1904/tf/1.0.0 review-site --model openrouter/free --dataset-context n1904-notes.md --describe-features lemma,tense,frame --model-attribution overview

Open the three feature pages in review-site/features/ and compare the prose with the source metadata. The rest of the site is built normally, with measured data and no generated paragraph on unselected pages. Use a separate review directory if you want to keep an existing enriched site. Feature names are case-sensitive and omit the .tf extension.

Each uncached feature gets its own request containing its profile and the full notes. Even with one named model, a request has no conversation history from earlier features. Include only notes you intend to share with your selected provider. OpenRouter’s free router may choose different models across requests.

When ready, remove --describe-features lemma,tense,frame to enrich all features. With the same provider, model, evidence and notes, reviewed responses are reused from the cache. Editing the notes changes the request and triggers fresh descriptions. Renaming the file with the same contents reuses the cache. Omit --dataset-context to work from feature profiles alone.

Choose where to credit the model

The default shows the provider and responding model on each enriched feature page. Use --model-attribution overview to list the distinct credits once on the corpus homepage, or none to hide them. All modes retain “Generated description”. If the provider omits a model ID, or an older cached response contains only the text, the credit identifies the model as requested. Changing this display option reuses the same prose.

For a completely offline build, omit the model, feature selection and editor notes.
